*Starting on the basis of the Onboarding Layer structure and Google OAuth configuration.*

Today was mostly architecture day — figuring out how Theo should be shaped before we dig into real Google login. A lot of naming got cleaned up so “onboarding” stops meaning three different things.

---

## The big picture we’re aiming for

Theo is a single-account browser. One Google account at a time. No Chrome-style profile picker with a list of people. If someone else needs to use it, they log out and log in as themselves — that replaces the one session slot.

Login + the rest of the early experience aren’t throwaway screens. Together they’re the **account foundation**: who is signed in, basic saved data, then later the browser chrome hooks into that same identity. When we build the webview and agent stuff, we shouldn’t have to reinvent “who is this user?”

For now, the only Google profile fields we care about after OAuth are **first name** and **profile picture**. Tokens stay in the main process forever — React never sees them.

---

## Electron mental model (so we don’t confuse ourselves)

- **`main.ts`** — Node side. Creates the window, owns secrets, talks to disk/Google, handles IPC. It does *not* paint the UI.
- **`preload.ts`** — Tiny bridge. Exposes `window.theo` so React can ask main for things safely.
- **`renderer.tsx`** — Boots React into `#root`. Think of it as the thalamus: it mounts the app and gets out of the way.
- **`BrowserWindow`** — A live window object main creates at runtime, not a constant blob of data. One app window for now; tabs later live *inside* chrome (webview/BrowserView), not as a pile of OS windows.

React doesn’t “render into BrowserWindow” magically — main loads `index.html`, which loads `renderer.tsx`, which mounts our UI into the DOM. Same as a normal Vite app, just living inside a desktop shell.

`window.theo` is just our private API on the page. We invented the name. Preload puts it there. Dashboard calling `window.theo.openExternal(...)` is really “please ask main to open this URL.”

## Folder structure we settled on

```
src/
  main.ts
  preload.ts
  renderer.tsx
  index.css
  vite-env.d.ts          ← TypeScript declarations for Vite globals, image imports, window.theo

  onboarding-layer/
    OnboardingLayer.tsx  ← the gate for this shell (login check later; Dashboard for now)
    pages/
      Auth.tsx           ← fossil background lives here now (moved off global body)
      Dashboard.tsx

  browser-chrome/
    BrowserChrome.tsx    ← empty stub for later
    pages/               ← ready for the same pattern
```

`OnboardingLayer` replaced what used to be `App.tsx`. Renderer mounts `OnboardingLayer` directly today. When we leave Dashboard for the real browser, something thin will swap to `BrowserChrome` — that’s a *different* story from login, and we don’t need to overbuild it yet.

Keeping main/preload/renderer/css/types at `src/` root is normal for Electron Forge + Vite at this size. If main grows (auth modules, agent threads), we split **main into folders of `.ts` files** — not a second main process per UI shell.

## Login gate & Zustand (decision)

How do we know Auth vs Dashboard on startup?

Main holds an encrypted session (refresh token = “stay logged in until logout”). Renderer asks via something like `window.theo.auth.getSession()`.

We debated `useEffect` in the root vs a Zustand store. Honest take:

- Root `useEffect` + a ready flag is fine for a tiny app.
- We’re going to have several pages that all care about “are they signed in?” (Auth, Dashboard, later BYOK, mid-task session drop, etc.). Local state only in one giant root file gets messy.

**Decision:** use Zustand for **login gating only** right now — `LOADING | SIGNED_OUT | SIGNED_IN` (plus profile fields when we have them). Not responsible for Dashboard → Browser. That transition stays separate.

Store idea:

- Auth store talks to `theo.auth.*`
- `OnboardingLayer` reads status and shows Auth or the signed-in onboarding pages
- Later we can subscribe to session drops from main into the same store

We have **not** installed Zustand or wired auth IPC yet. That’s next work, not done today.

## Google OAuth shape (still the plan, not built)

Authorization Code + PKCE in **main**. Preload is only the bridge. Flow roughly:

1. User hits Continue with Google on Auth
2. Main builds PKCE + state, opens Google, catches redirect
3. Exchanges code for access + refresh tokens
4. Pulls first name + picture
5. Saves encrypted session with `safeStorage`
6. Returns safe profile to the UI — no tokens

Cold start: if refresh token exists → skip Auth. Access tokens expire ~hourly; main refreshes quietly. Logout clears the vault.

Later Google APIs (Drive etc.) reuse that vault — same login.

---

## Main process as it grows

One main process forever. When it gets fat, extract modules main imports, e.g.:

- `main/window.ts` — window create, zoom, menu
- `main/auth/*` — OAuth, token store, auth IPC
- `main/agent/*` — later threads / a11y / actions

Don’t make `onboarding.ts` in main just to mirror the React folder unless main actually owns that logic. UI stays under `onboarding-layer/`; secrets and Google stay under main auth modules.
